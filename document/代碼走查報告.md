## 2. 項目概覽與技術棧

HRAI / InnerAI HR 系統是一個招聘流程工作台，核心功能包括帳號登入註冊、職位字典、職缺管理、CV 上傳與 AI 解析、候選人管理、面試安排、黑名單、已入職人員與項目管理。

| 層級 | 技術/文件 | 走查觀察 |
| --- | --- | --- |
| 前端 | Vue 3、Vite | 自建輕量 router，主要業務頁集中在 `/main` 工作台內切換。 |
| 後端 | Node.js 原生 HTTP server、ESM | `server/index.js` 承擔路由、認證、資料查詢、CV、LLM、面試、項目等大量責任。 |
| 資料庫 | MySQL 8、`mysql2` | 啟動時自動建庫建表與補欄，未拆分版本化 migration。 |
| AI | OpenAI-compatible Chat Completions | 支援 `LLM_*` / `CV_LLM_*` 配置，CV 抽取與職位匹配依賴 LLM。 |
| 文件存儲 | `server/storage/cv` | CV 原檔寫入本機文件系統，資料庫保存 storage key。 |
| 部署 | Docker Compose | MySQL、後端、前端三服務；Docker 後端會安裝 Python PDF 抽取依賴。 |

## 4. 後端代碼走查

### 4.1 架構

- `server/index.js` 約 6684 行，承擔路由、認證、授權、DB 操作、檔案操作、CV 解析、LLM、日誌、面試狀態定時刷新與項目管理。
- 目前路由透過大量 `if`/正則分支處理，例如 `server/index.js:6416` 起的 API 分派段。
- 短期可運行，但長期新增接口容易出現順序依賴、回歸難測與局部修改風險。

### 4.2 正向觀察

- 密碼使用 PBKDF2-SHA512 + salt：`server/index.js:154`。
- token 只保存 SHA-256 hash：`server/index.js:161`、`server/index.js:613`。
- SQL 查詢多數使用參數化 `pool.query(sql, params)`，整體 SQL injection 風險相對可控。
- CV 文件名有 `sanitizeFileName` 處理：`server/index.js:410`。
- 黑名單使用標準化電話與 Email 進行命中：`server/index.js:1993`、`server/index.js:1995`、`server/index.js:3518`。
- LLM API Key 在日誌中做了遮罩：`server/scripts/logger.js:71`、`server/scripts/logger.js:181`。

### 4.3 路由與權限

- `ROLE_ACCESS_ROUTES` 目前只對少量路由限制角色，例如 `/api/users`、`/api/job-dictionary`：`server/index.js:321` 至 `server/index.js:325`。
- `enforceRoleAccess` 對無角色規則且非寫請求的 API 直接放行：`server/index.js:351`。
- 因此多數 GET API 在後端層面不要求 token，包括候選人列表、CV 預覽/下載、職缺候選人、項目、人員、黑名單、面試列表等。

## 5. 資料庫與資料一致性走查

### 5.1 表結構

資料表由 `server/scripts/database/index.js` 啟動時建立：

- 帳號：`users`、`auth_tokens`
- 招聘：`candidates`、`candidate_cvs`、`candidate_cv_extractions`、`job_posts`、`candidate_cv_job_matches`、`job_post_applications`、`job_post_application_status_history`
- 人員/項目：`personnel`、`projects`、`project_personnel_assignments`、`project_personnel_movements`
- 黑名單：`candidate_blacklist`

表關係已在 `document/表關係.md` 中重新整理。

### 5.2 正向觀察

- 核心表有外鍵與 cascade/set null 行為。
- `job_post_application_status_history` 可保存流程與面試歷史。
- `candidate_blacklist` 不綁候選人 FK，允許先建黑名單再命中後續候選人。
- 職缺保存 `job_snapshot_json`，避免職位字典後續變動影響既有職缺。

### 5.3 風險觀察

- 啟動時做多個 `CREATE TABLE` / `ALTER TABLE` / 補資料操作，見 `server/scripts/database/index.js:34`、`server/scripts/database/index.js:221`、`server/scripts/database/index.js:304`。
- `owner_user_id`、`interviewer_user_id`、`operator_user_id` 是邏輯關係，程式查詢 join `users`，但 DDL 未設外鍵。
- `job_post_applications.candidate_cv_id` 有唯一鍵，代表同一 CV 只能對應一筆投遞；若未來要同一 CV 投多個職缺，需要調整。
- 編輯 AI 解析欄位後會同步候選人主檔並重算匹配，候選人主檔更像「最新履歷版本」，不是「投遞當時快照」。

## 10. 建議後續任務

### 10.1 優先修復

1. 後端 GET API 預設加認證，只保留明確 public allowlist。
2. 移除驗證碼 console 輸出，正式環境接入發送服務。
3. 從 git 中移除 `.env` 與已追蹤 CV PDF，補 `.env.example` 並輪換敏感值。
4. 為項目、人員、黑名單、候選人等頁面統一前端 API client 與 auth header。

### 10.2 中期改造

1. 將 `server/index.js` 拆成 routes/services/repositories。
2. 建立版本化資料庫 migration。
3. 將職位字典改為 atomic file write 或資料表版本管理。

### 10.3 測試補強

1. API 權限測試：未登入、viewer、hr、admin 對 GET/POST/PATCH/DELETE 的行為。
2. CV 流程測試：cache、parse、intake、過期 cache、批量來源缺失、LLM JSON 修復。
3. 候選人流程測試：狀態歷史、面試狀態自動校正、批量刪除、黑名單命中。
4. 項目流程測試：新增人員、CSV 匯入、調動、移出、已入職候選人轉項目。
5. 配置/部署測試：Docker 默認環境、server 子項目依賴、前端 API base URL。

## 11. 總結

整體來看，HRAI 已具備完整招聘工作台功能，CV 解析、職位字典、候選人狀態歷史、面試排程、項目人員流轉等核心能力已落地。當前最需要優先處理的是後端讀接口授權、敏感文件追蹤、驗證碼輸出、CV 上傳資源限制與依賴/部署一致性。完成這些修復後，再進行後端拆分、migration、共用 API client 與自動化測試補強，系統的安全性、可維護性與交付穩定性會明顯提升。
