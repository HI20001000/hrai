# HRAI 系統資料表設計與表關係

本文依據當前項目源碼整理，主要來源為：

- `server/scripts/database/index.js`：資料庫建立、資料表 DDL、相容性補欄、索引與外鍵。
- `server/index.js`：API 對資料表的讀寫、狀態值、邏輯關係與刪除處理。
- `src/scripts/candidateApplicationStatus.js`、`src/views/JobPosts.vue`、`src/scripts/cvSource.js`：前端狀態選項與業務枚舉。

最後更新日期：2026-06-02

## 1. 資料庫初始化

### 1.1 資料庫名稱

後端啟動時會先確保資料庫存在，預設資料庫名稱為 `hrai`。

| 配置項 | 說明 |
| --- | --- |
| `HRAI_DATABASE` | 優先使用的 HRAI 資料庫名稱。 |
| `MYSQL_DATABASE` | 未配置 `HRAI_DATABASE` 時使用。 |
| 預設值 | `hrai` |

建立資料庫時使用：

```sql
CREATE DATABASE IF NOT EXISTS `資料庫名`
CHARACTER SET utf8mb4
COLLATE utf8mb4_unicode_ci;
```

### 1.2 初始化流程

後端啟動時會依序執行：

1. 建立資料庫。
2. 建立認證與帳號表：`users`、`auth_tokens`。
3. 建立候選人、CV、職缺、投遞、面試、內部人員、項目與黑名單相關表。
4. 對既有版本做相容性補欄，例如：
   - `users.username`
   - `users.role`
   - `users.avatar_text`
   - `users.avatar_bg_color`
   - `candidate_cvs.source`
   - `job_post_applications.remark`
   - `job_post_applications.first_interview_arrangement`
   - `job_post_applications.interview_*`
   - `job_post_applications.owner_user_id`
   - `job_post_application_status_history.operator_user_id`
   - `candidate_blacklist.normalized_phone`
   - `candidate_blacklist.normalized_email`
5. 將舊狀態 `submitted` 遷移為 `screening`。
6. 若系統中沒有 `admin`，會將最早建立的使用者調整為 `admin`。
7. 為既有投遞資料補一筆初始狀態歷史到 `job_post_application_status_history`。

## 2. 資料表總覽

| 表名 | 類型 | 主要用途 | 關鍵關係 |
| --- | --- | --- | --- |
| `users` | 帳號認證 | 登入帳號、角色、使用者資料、密碼 hash/salt。 | 被 `auth_tokens` 外鍵關聯；被投遞 owner/interviewer/operator 邏輯關聯。 |
| `auth_tokens` | 帳號認證 | 登入 token hash 與到期時間。 | `user_id -> users.id`，刪除 user 時 cascade。 |
| `candidates` | 招聘主檔 | 候選人姓名、Email、電話。 | 被 CV、CV 解析、匹配、投遞關聯。 |
| `candidate_cvs` | CV 檔案 | 候選人 CV 檔案版本、儲存位置、來源與檔案 hash。 | `candidate_id -> candidates.id`。 |
| `candidate_cv_extractions` | AI 解析 | CV 原文、AI 分析 JSON、目標職位。 | `candidate_id -> candidates.id`；`candidate_cv_id -> candidate_cvs.id`。 |
| `job_posts` | 職缺 | 已建立職缺、職位字典 key、職位快照與狀態。 | 被 `job_post_applications` 關聯。 |
| `candidate_cv_job_matches` | 匹配結果 | CV 與職位字典的匹配分數、等級、優勢與差距。 | `candidate_id -> candidates.id`；`candidate_cv_id -> candidate_cvs.id`。 |
| `job_post_applications` | 投遞/流程 | 候選人對具體職缺的投遞、流程狀態、面試安排與匹配摘要。 | 連接 `job_posts`、`candidates`、`candidate_cvs`。 |
| `job_post_application_status_history` | 流程歷史 | 投遞狀態、面試安排、面試結果與操作歷史。 | `application_id -> job_post_applications.id`。 |
| `personnel` | 內部人員 | 已入職/內部人員主檔。 | 自關聯主管；被項目、分配、調動關聯。 |
| `projects` | 項目 | 項目主檔、狀態、負責人與日期。 | `owner_personnel_id -> personnel.id`。 |
| `project_personnel_assignments` | 項目人員 | 人員與項目的當前安排。 | `project_id -> projects.id`；`personnel_id -> personnel.id`。 |
| `project_personnel_movements` | 項目調動歷史 | 項目人員加入、更新、調動、移出記錄。 | 關聯分配、人員、調出/調入項目。 |
| `candidate_blacklist` | 黑名單 | 候選人黑名單與風險原因。 | 不設 FK，透過標準化電話/Email 邏輯命中候選人。 |

補充：

- `finance-job-positions.json` 是職位字典檔案，不是資料表。職缺建立時會把字典內容固化為 `job_posts.job_snapshot_json`。
- CV 原始檔案儲存在 `server/storage/cv`，資料表只保存 `storage_key`、檔名、hash 與檔案資訊。

## 3. 核心 ER 關係

### 3.1 帳號與登入 token

```text
users
  1 ───< auth_tokens
```

| 關係 | 類型 | 刪除行為 |
| --- | --- | --- |
| `auth_tokens.user_id -> users.id` | 實體外鍵 | `ON DELETE CASCADE` |

說明：

- 使用者登入後產生 token，資料庫保存的是 token hash。
- 刪除使用者時，其登入 token 會一併刪除。

### 3.2 候選人、CV、解析與匹配

```text
candidates
  1 ───< candidate_cvs
  1 ───< candidate_cv_extractions
  1 ───< candidate_cv_job_matches

candidate_cvs
  1 ───  candidate_cv_extractions
  1 ───< candidate_cv_job_matches
```

| 關係 | 類型 | 刪除行為 |
| --- | --- | --- |
| `candidate_cvs.candidate_id -> candidates.id` | 實體外鍵 | `ON DELETE CASCADE` |
| `candidate_cv_extractions.candidate_id -> candidates.id` | 實體外鍵 | `ON DELETE CASCADE` |
| `candidate_cv_extractions.candidate_cv_id -> candidate_cvs.id` | 實體外鍵 | `ON DELETE CASCADE` |
| `candidate_cv_job_matches.candidate_id -> candidates.id` | 實體外鍵 | `ON DELETE CASCADE` |
| `candidate_cv_job_matches.candidate_cv_id -> candidate_cvs.id` | 實體外鍵 | `ON DELETE CASCADE` |

說明：

- 一位候選人可以有多份 CV。
- 同一候選人的 CV 以 `version_no` 區分版本。
- 每份 CV 最多對應一筆 AI 解析記錄，透過 `candidate_cv_extractions.candidate_cv_id` 唯一鍵控制。
- 匹配表保存 CV 對職位字典中職位的候選匹配結果。

### 3.3 職缺、投遞、候選人與 CV

```text
job_posts
  1 ───< job_post_applications >─── 1 candidates
                                      ^
                                      |
                                  candidate_cvs
```

| 關係 | 類型 | 刪除行為 |
| --- | --- | --- |
| `job_post_applications.job_post_id -> job_posts.id` | 實體外鍵 | `ON DELETE CASCADE` |
| `job_post_applications.candidate_id -> candidates.id` | 實體外鍵 | `ON DELETE CASCADE` |
| `job_post_applications.candidate_cv_id -> candidate_cvs.id` | 實體外鍵 | `ON DELETE CASCADE` |
| `job_post_applications.owner_user_id -> users.id` | 邏輯關係 | 無資料庫 FK |
| `job_post_applications.interviewer_user_id -> users.id` | 邏輯關係 | 無資料庫 FK |

說明：

- `job_post_applications` 是招聘流程主交易表，將職缺、候選人與 CV 連起來。
- `candidate_cv_id` 有唯一鍵 `uniq_job_post_application_cv`，代表同一份 CV 在目前設計中只會對應一筆具體職缺投遞。
- `owner_user_id` 表示對接/負責 HR，程式查詢時會 join `users`。
- `interviewer_user_id` 表示面試官使用者，程式查詢時會 join `users`。
- 上述兩個使用者欄位目前沒有 DDL 外鍵，屬於邏輯關係。

### 3.4 投遞流程與狀態歷史

```text
job_post_applications
  1 ───< job_post_application_status_history

users
  1 ───< job_post_application_status_history.operator_user_id     (邏輯關係)
  1 ───< job_post_application_status_history.interviewer_user_id  (邏輯關係)
```

| 關係 | 類型 | 刪除行為 |
| --- | --- | --- |
| `job_post_application_status_history.application_id -> job_post_applications.id` | 實體外鍵 | `ON DELETE CASCADE` |
| `job_post_application_status_history.operator_user_id -> users.id` | 邏輯關係 | 無資料庫 FK |
| `job_post_application_status_history.interviewer_user_id -> users.id` | 邏輯關係 | 無資料庫 FK |

說明：

- 每次新增、修改投遞狀態或面試安排，可形成狀態歷史。
- 初始化時若某筆投遞沒有歷史，會自動補入一筆與主表當前狀態一致的歷史記錄。
- `operator_user_id` 記錄操作人，`interviewer_user_id` 記錄面試官，程式查詢時會 join `users`，但資料庫未建立外鍵。

### 3.5 內部人員、項目與調動

```text
personnel
  ├── personnel.manager_personnel_id -> personnel.id
  ├──< projects.owner_personnel_id
  ├──< project_personnel_assignments >── projects
  └──< project_personnel_movements

project_personnel_assignments
  1 ───< project_personnel_movements
```

| 關係 | 類型 | 刪除行為 |
| --- | --- | --- |
| `personnel.manager_personnel_id -> personnel.id` | 實體外鍵 | `ON DELETE SET NULL` |
| `projects.owner_personnel_id -> personnel.id` | 實體外鍵 | `ON DELETE SET NULL` |
| `project_personnel_assignments.project_id -> projects.id` | 實體外鍵 | `ON DELETE CASCADE` |
| `project_personnel_assignments.personnel_id -> personnel.id` | 實體外鍵 | `ON DELETE CASCADE` |
| `project_personnel_movements.assignment_id -> project_personnel_assignments.id` | 實體外鍵 | `ON DELETE SET NULL` |
| `project_personnel_movements.personnel_id -> personnel.id` | 實體外鍵 | `ON DELETE CASCADE` |
| `project_personnel_movements.from_project_id -> projects.id` | 實體外鍵 | `ON DELETE SET NULL` |
| `project_personnel_movements.to_project_id -> projects.id` | 實體外鍵 | `ON DELETE SET NULL` |

說明：

- `personnel` 同時用於已入職名單與項目人員主檔。
- `projects.owner_personnel_id` 指向項目負責人。
- `project_personnel_assignments` 保存目前人員與項目的關係。
- `project_personnel_movements` 保存人員加入、更新、調動、移出的歷史；即使項目或分配刪除，也盡量保留歷史脈絡。

### 3.6 黑名單與候選人

```text
candidate_blacklist
  ├── normalized_phone
  └── normalized_email

candidates
  ├── phone
  └── email
```

說明：

- `candidate_blacklist` 不與 `candidates` 建立外鍵。
- 系統透過標準化後的 `normalized_phone`、`normalized_email` 與候選人的電話/Email 做邏輯命中。
- 這種設計允許先建立黑名單，再於後續候選人入庫或列表查詢時提示風險。

## 4. 資料表詳細設計

### 4.1 `users`

用途：保存登入帳號、角色、使用者個人設定與密碼資訊。

| 欄位 | 型別 | Null | 預設值 | Key | 說明 |
| --- | --- | --- | --- | --- | --- |
| `id` | `BIGINT` | No | Auto Increment | PK | 使用者主鍵。 |
| `email` | `VARCHAR(255)` | No | 無 | UK | 登入 Email，唯一。 |
| `username` | `VARCHAR(80)` | Yes | `NULL` |  | 顯示名稱。 |
| `role` | `VARCHAR(40)` | No | `hr` |  | 角色：`admin`、`hr`、`viewer`。 |
| `avatar_text` | `VARCHAR(16)` | Yes | `NULL` |  | 頭像文字。 |
| `avatar_bg_color` | `VARCHAR(20)` | Yes | `NULL` |  | 頭像背景色。 |
| `password_hash` | `VARCHAR(255)` | No | 無 |  | 密碼 hash。 |
| `password_salt` | `VARCHAR(255)` | No | 無 |  | 密碼 salt。 |
| `created_at` | `TIMESTAMP` | Yes | `CURRENT_TIMESTAMP` |  | 建立時間。 |

索引與約束：

| 名稱 | 類型 | 欄位 |
| --- | --- | --- |
| Primary Key | PK | `id` |
| Email Unique | Unique | `email` |

補充：

- 密碼使用 PBKDF2-SHA512 + salt 保存。
- 首位註冊使用者為 `admin`，後續註冊預設為 `hr`。
- 啟動時若無 `admin`，會將最早建立的使用者改為 `admin`。

### 4.2 `auth_tokens`

用途：保存登入 session token hash 與到期時間。

| 欄位 | 型別 | Null | 預設值 | Key | 說明 |
| --- | --- | --- | --- | --- | --- |
| `id` | `BIGINT` | No | Auto Increment | PK | token 主鍵。 |
| `user_id` | `BIGINT` | No | 無 | FK, IDX | 對應 `users.id`。 |
| `token_hash` | `VARCHAR(255)` | No | 無 |  | token 的 SHA-256 hash。 |
| `expires_at` | `DATETIME` | No | 無 | IDX | 到期時間。 |
| `created_at` | `TIMESTAMP` | Yes | `CURRENT_TIMESTAMP` |  | 建立時間。 |

索引與約束：

| 名稱 | 類型 | 欄位 | 說明 |
| --- | --- | --- | --- |
| Primary Key | PK | `id` | 主鍵。 |
| `idx_user_id` | Index | `user_id` | 查詢使用者 token。 |
| `idx_expires_at` | Index | `expires_at` | 清理或判斷到期 token。 |
| `fk_auth_user` | FK | `user_id -> users.id` | `ON DELETE CASCADE`。 |

### 4.3 `candidates`

用途：保存候選人主檔。

| 欄位 | 型別 | Null | 預設值 | Key | 說明 |
| --- | --- | --- | --- | --- | --- |
| `id` | `BIGINT` | No | Auto Increment | PK | 候選人主鍵。 |
| `full_name` | `VARCHAR(120)` | No | 無 | IDX | 候選人姓名。 |
| `email` | `VARCHAR(255)` | Yes | `NULL` | IDX | Email。 |
| `phone` | `VARCHAR(40)` | Yes | `NULL` |  | 電話。 |
| `created_at` | `TIMESTAMP` | Yes | `CURRENT_TIMESTAMP` |  | 建立時間。 |
| `updated_at` | `TIMESTAMP` | Yes | `CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` |  | 更新時間。 |

索引與約束：

| 名稱 | 類型 | 欄位 |
| --- | --- | --- |
| Primary Key | PK | `id` |
| `idx_candidate_name` | Index | `full_name` |
| `idx_candidate_email` | Index | `email` |

補充：

- 候選人是否重複主要由程式透過姓名、Email、電話進行判斷。
- 表內未對 Email 或電話設唯一鍵，避免不同來源資料不完整時無法入庫。

### 4.4 `candidate_cvs`

用途：保存候選人 CV 檔案版本與本機儲存資訊。

| 欄位 | 型別 | Null | 預設值 | Key | 說明 |
| --- | --- | --- | --- | --- | --- |
| `id` | `BIGINT` | No | Auto Increment | PK | CV 主鍵。 |
| `candidate_id` | `BIGINT` | No | 無 | FK, IDX, UK | 對應 `candidates.id`。 |
| `version_no` | `INT` | No | 無 | UK | 候選人 CV 版本號。 |
| `storage_provider` | `VARCHAR(30)` | No | `local` |  | 儲存提供方，目前預設本機。 |
| `storage_key` | `VARCHAR(500)` | No | 無 |  | 本機檔案 key。 |
| `original_filename` | `VARCHAR(255)` | No | 無 |  | 原始檔名。 |
| `mime_type` | `VARCHAR(100)` | No | 無 |  | MIME type。 |
| `file_size` | `BIGINT` | No | 無 |  | 檔案大小。 |
| `sha256` | `CHAR(64)` | No | 無 |  | 檔案 SHA-256。 |
| `source` | `VARCHAR(20)` | Yes | `NULL` |  | CV 來源。 |
| `uploaded_at` | `TIMESTAMP` | Yes | `CURRENT_TIMESTAMP` | IDX | 上傳時間。 |

索引與約束：

| 名稱 | 類型 | 欄位 | 說明 |
| --- | --- | --- | --- |
| Primary Key | PK | `id` | 主鍵。 |
| `idx_candidate_id` | Index | `candidate_id` | 候選人 CV 查詢。 |
| `idx_candidate_uploaded_at` | Index | `uploaded_at` | 上傳時間排序。 |
| `uniq_candidate_version` | Unique | `candidate_id, version_no` | 同一候選人 CV 版本唯一。 |
| `fk_candidate_cvs_candidate` | FK | `candidate_id -> candidates.id` | `ON DELETE CASCADE`。 |

補充：

- `source` 來源值由前端/後端流程控制，當前業務來源為 `BOSS`、`智聯`、`內推`。
- 檔案實體位於 `server/storage/cv`，刪除職缺/投遞時程式會嘗試清理相關 CV 檔案。

### 4.5 `candidate_cv_extractions`

用途：保存 CV 文字抽取結果與 AI 解析結果。

| 欄位 | 型別 | Null | 預設值 | Key | 說明 |
| --- | --- | --- | --- | --- | --- |
| `id` | `BIGINT` | No | Auto Increment | PK | 解析記錄主鍵。 |
| `candidate_id` | `BIGINT` | No | 無 | FK, IDX | 對應 `candidates.id`。 |
| `candidate_cv_id` | `BIGINT` | No | 無 | FK, UK | 對應 `candidate_cvs.id`，每份 CV 最多一筆解析。 |
| `target_position` | `VARCHAR(255)` | Yes | `NULL` |  | AI 或人工整理出的目標職位。 |
| `cv_text` | `LONGTEXT` | Yes | `NULL` |  | 原始 CV 文字抽取結果。 |
| `extracted_text` | `LONGTEXT` | Yes | `NULL` |  | AI 分析 JSON 文字。 |
| `created_at` | `TIMESTAMP` | Yes | `CURRENT_TIMESTAMP` |  | 建立時間。 |

索引與約束：

| 名稱 | 類型 | 欄位 | 說明 |
| --- | --- | --- | --- |
| Primary Key | PK | `id` | 主鍵。 |
| `uniq_candidate_cv_extraction` | Unique | `candidate_cv_id` | 每份 CV 一筆解析。 |
| `idx_candidate_extractions_candidate` | Index | `candidate_id` | 候選人解析查詢。 |
| `fk_candidate_cv_extractions_candidate` | FK | `candidate_id -> candidates.id` | `ON DELETE CASCADE`。 |
| `fk_candidate_cv_extractions_cv` | FK | `candidate_cv_id -> candidate_cvs.id` | `ON DELETE CASCADE`。 |

### 4.6 `job_posts`

用途：保存系統建立的職缺與職位字典快照。

| 欄位 | 型別 | Null | 預設值 | Key | 說明 |
| --- | --- | --- | --- | --- | --- |
| `id` | `BIGINT` | No | Auto Increment | PK | 職缺主鍵。 |
| `title` | `VARCHAR(255)` | No | 無 |  | 職缺標題。 |
| `job_key` | `VARCHAR(120)` | No | 無 | IDX | 職位字典 key。 |
| `job_snapshot_json` | `LONGTEXT` | No | 無 |  | 建立職缺時的職位字典快照。 |
| `status` | `VARCHAR(40)` | No | `open` | IDX | 職缺狀態。 |
| `created_at` | `TIMESTAMP` | Yes | `CURRENT_TIMESTAMP` |  | 建立時間。 |
| `updated_at` | `TIMESTAMP` | Yes | `CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` |  | 更新時間。 |

索引與約束：

| 名稱 | 類型 | 欄位 |
| --- | --- | --- |
| Primary Key | PK | `id` |
| `idx_job_posts_status` | Index | `status` |
| `idx_job_posts_job_key` | Index | `job_key` |

狀態值：

| 值 | 說明 |
| --- | --- |
| `open` | 開放中。 |
| `draft` | 草稿。 |
| `closed` | 已關閉。 |

補充：

- 職位字典來源為 `finance-job-positions.json`。
- `job_snapshot_json` 保存職缺建立當下的職位要求，避免字典日後變更影響既有職缺判斷。

## 6. 刪除與級聯行為

| 操作 | 資料庫行為 | 程式補充行為 |
| --- | --- | --- |
| 刪除 `users` | `auth_tokens` cascade 刪除。 | 需注意投遞 owner/interviewer/operator 只是邏輯關係，不會自動清空。 |
| 刪除 `candidates` | CV、解析、匹配、投遞 cascade 刪除。 | 候選人批量刪除會直接刪主表。 |
| 刪除 `candidate_cvs` | 解析、匹配、投遞 cascade 刪除。 | CV 檔案實體需由程式流程清理。 |
| 刪除 `job_posts` | 投遞 cascade 刪除。 | 程式刪職缺前會收集相關 CV storage key 並嘗試刪除檔案。 |
| 刪除 `job_post_applications` | 狀態歷史 cascade 刪除。 | 批量刪除投遞時會一併處理相關 CV。 |
| 刪除 `personnel` | 項目分配 cascade；調動歷史 cascade；主管欄位 set null。 | 刪除前程式會先將其他人員的 `manager_personnel_id` 清空。 |
| 刪除 `projects` | 項目人員分配 cascade；調動歷史中的項目欄位 set null。 | 歷史記錄盡量保留。 |
| 刪除 `project_personnel_assignments` | 調動歷史中的 `assignment_id` set null。 | 移出項目會寫入 movement 記錄。 |
| 刪除 `candidate_blacklist` | 無級聯。 | 黑名單與候選人無 FK。 |

## 9. 資料設計注意事項

1. `job_post_applications.candidate_cv_id` 是唯一鍵，同一份 CV 目前只能對應一筆投遞；若未來要支援同一 CV 投遞多個職缺，需要調整此唯一鍵。
2. `owner_user_id`、`interviewer_user_id`、`operator_user_id` 目前是邏輯關係，沒有資料庫 FK；刪除使用者時不會自動清空這些欄位。
3. `candidate_blacklist` 不綁定候選人 ID，而是用標準化電話/Email 做命中；這有利於先建黑名單，但需要在查詢與入庫流程中持續做命中判斷。
4. `job_snapshot_json` 保存職位字典快照，後續職位字典變更不會自動更新既有職缺。
5. `candidate_cv_extractions.extracted_text`、`candidate_cv_job_matches.raw_llm_json` 等欄位保存 JSON 文字，資料庫層未做 JSON 型別約束。
6. `project_personnel_movements` 主要保存歷史，不應作為當前項目人員狀態唯一來源；當前安排以 `project_personnel_assignments` 為準。
7. 多數狀態欄位使用 `VARCHAR`，狀態合法性主要由後端程式校驗，資料庫未設 CHECK 約束。
